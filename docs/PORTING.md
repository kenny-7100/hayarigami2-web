## 已验证的镜像内容

本次分析对象是仓库根目录的 `hg2.iso`。日期：2026-10-18。

- ISO 9660，PSP UMD 结构。
- PARAM.SFO 标题：`流行之神２携帶版`，DISC_ID：`ULJS00149`，DISC_VERSION：`1.02`，PSP_SYSTEM_VER：`3.95`。
- `BOOT.BIN` 和 `EBOOT.BIN` 是 MIPS ELF 32 位程序，不是可以复用的 JavaScript 或游戏源码。
- `DATA.DAT`：264,896,512 字节；`OP01.PMF`：21,487,616 字节。
- 关键词里可见中文词汇，标题也包含汉字本地化痕迹，但尚未核实汉化版本、汉化完整性和自定义字体映射。

## 可重复提取

运行 `npm run extract:game`，或 `python3 scripts/extract_game.py /path/to/hg2.iso`。

需要 Python 3 与 `bsdtar`（macOS 自带；Linux 通常安装 `libarchive-tools`）。脚本只读取 ISO，不运行任何原版程序。

输出：

- `output/iso-inspection/`：从 ISO 提取的工作文件。
- `output/extracted/`：46 个命名资源与 `story-index.json`。
- `public/game/`：5 张 PNG、Web 使用的资源清单和关键词。
- `manifest.json` 记录 DATA.DAT 的 SHA-256，以便追踪输入版本。

原始镜像、提取物都被 Git 忽略。Web 应用不依赖浏览器读取 ISO；部署构建前须在本地生成资源。

## NISPACK 结构（已验证）

DATA.DAT 内 `0x0F190000` 是内嵌 NISPACK 容器，包含 46 条记录。该容器只覆盖资源包的一部分，**不是整盘资源都已经解包**。

头部：

| 字段 | 偏移 | 格式 |
| --- | --- | --- |
| magic | 0 | `NISPACK\0`，8 字节 |
| endian | 8 | little-endian uint32，本镜像为 0 |
| count | 12 | little-endian uint32，本镜像为 46 |

随后每条记录 44 字节：32 字节 NUL 结尾 ASCII 文件名，uint32 相对偏移，uint32 文件长度，uint32 未解释字段（可能是时间戳）。**偏移相对于 NISPACK 头部，不相对于 DATA.DAT 起点。** 所有提取记录均校验路径、索引范围和数据边界。

包括：`story.dat`、`story.did`、`keyword.dat`、`logic.dat`、`OccultFile.dat`、`Selecter.dat`、`anm0000.dat`、`jis2ucs.bin`、字体纹理、TXP、音效资源及 3 张标准 PNG。

## 剧情脚本（部分解析）

`story.dat` 为 4,637,052 字节。

- 起始两个 little-endian uint32 分别为索引区结束偏移 `0x4248` 与索引数量 `2120`。
- 索引项为 `(id:uint32, offset:uint32)`，每项 8 字节；满足 `8 + 2120 * 8 == 0x4248`。
- 所有偏移在文件内且单调递增。可根据下一偏移得到每个记录的长度。
- 不应把这些记录称为“章节”或“对话条数”：其中包含控制脚本。
- 记录内可见以 `FF` 开头的指令头；第二字节疑似长度，随后两字节疑似操作码。某些短记录表现为四字节对齐，但文本内嵌、零填充等情况尚未完整解释，不能据此直接遍历执行。
- 正文片段包含大量 `68 xx` 至 `7E xx` 字节对。CP932、UTF-16LE、直接 JIS 查表均不能正确还原。
- `jis2ucs.bin` 有 65,536 个 uint16，部分标准 JIS 映射有效，如 `0x2422 -> U+3042`，但不能直接用于正文。
- 不要把看起来像文字的乱码直接存为剧情 JSON，也不要默认物理顺序等于剧情执行顺序。

`story.did`：219,324 字节；其语义未解析。

## 关键词（初步解析）

`keyword.dat` 起始 uint32 记录数为 433。每条固定索引长度 28 字节。当前解析每条前 8 字节：`id:uint16`、`byteLength:uint16`、`textOffset:uint32`。偏移相对于 keyword.dat 起点。

按 CP932 解码后有 432 条非空名称，可检索。其余字段似乎还关联附加文本，但未确认语义。CP932 能得到部分可读内容，却不保证与汉化字库逐字一致；网页已明确这一限制。

## 下一步的实施顺序

1. 解码字形：追踪 EBOOT 的文字读取与字体查表函数，确认正文编码和汉化字库对应关系；以游戏实际画面核对一句完整对白。单纯字符串扫描不足以保证正确。
2. 解析最小剧情：确定第一段实际入口和显示文字、换行、等待、背景、跳转指令。建立逐指令日志与保留原始偏移的中间表示。
3. 解析美术：定位 NISPACK 之外的资源索引，解码 TXP/字体纹理；先验证一张背景和一张透明立绘。
4. 实现 TypeScript 解释器：明确支持的 opcode；遇到未支持指令停止并报告原始偏移，不能静默跳过条件或跳转。
5. 实现首段可玩内容：由原始脚本转换场景，加入对话推进、历史、第一处分支与版本化存档，再对照原游戏检查。
6. 扩展系统：根据实际指令实现推理、自问自答、路线和解锁条件；建立分支覆盖用例，逐章验收。

建议架构：`ISO -> 提取器 -> 保留原始 ID/偏移的场景中间格式 -> TypeScript 状态机 -> React 阅读器`。游戏状态应与 UI 状态分离；存档至少包含脚本 ID、指令位置、标志位、变量、解锁记录、场景状态和数据版本。不要在编码与指令未验证前编造剧情内容或分支。
